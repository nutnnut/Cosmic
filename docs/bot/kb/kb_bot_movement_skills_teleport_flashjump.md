**Reverse-engineered ground truth** (from `logs/monitored-packets-teleportspd109jump105.log`, `flashjumpspeed100jump100.log`, `flashjumpspeed138jmp102.log`):
- Teleport distance = WZ `range` key (NOT `x` — earlier agents misread): 130 (L1–10) → 140 (L15) → 150 (L20). **Bots modelled at MAX range 150 always** (graph not keyed by teleport level; mages max it fast; bots move directly so no skill-cast enforcement) → dropped per-edge distance field, filter is just "has teleport". Vertical teleport snaps to the FURTHEST platform within range (no throttle — a L1/130 mage would reach a nearer platform, but we don't model that). Teleport ids: `FPWizard/ILWizard/Cleric/BlazeWizard/Evan.TELEPORT` (base Magician 2001002 = Magic Guard, NOT teleport).
- Flash Jump impulse = hardcoded CLIENT constant (WZ has only `mpCon`, no distance): mid-air ONE-TIME set velocity to **(±550 horizontal, −350 vertical) px/s**, injected at APEX (velY≥0). 550 is a hard H cap (didn't scale w/ 138% speed). Initial jump vel = −555·(jump/100). FJ ids: `Hermit/NightWalker.FLASH_JUMP`. Move cmd 6.
- MOVE_PLAYER recv(0x29) = `[01][4B field-CRC][startX:2][startY:2][numCmds:1][cmds][keypad+pos trailer]`; broadcast(0xB9) = `[cid:4][unk:4][numCmds:1][cmds]`. parseMovement (AbstractMovementPacketHandler): teleport=cmd 3/4, fj=cmd 6.

**Architecture:**
- CROSS-region edges in the shared profile-keyed graph (`BotNavigationGraphProvider`, GRAPH_VERSION 59→60): `addTeleportEdges` (horizontal ±150 + vertical up/down, anchor-based, `findRegionBelow` snap, SAME-region landings excluded — they'd be A* self-loops) + `addFlashJumpEdges` (`simulateFlashJumpLanding`, emitted only where a normal jump from the same anchor can't already reach). EdgeType += TELEPORT, FLASH_JUMP. Constants `TELEPORT_RANGE_PX=150`/`TELEPORT_Y_SNAP_PX=70` are package-visible (SSOT, shared w/ manager).
- Physics (`BotPhysicsEngine`): `FLASH_JUMP_H/V_PXS` Config + `flashJumpH/VPerTick()` (px/tick = px/s ×0.05 = ±27.5/−17.5). Apex injection in `stepAirborne` gated on `entry.pendingFlashJump` (applyAirSteering is a no-op above the input band so the dash survives; sets fixedAirArc). `simulateLanding` parameterized with optional `FlashImpulse`. `launchAirborne` clears `pendingFlashJump`. Teleport exec reuses `teleportTo`.
- Manager (`BotNavigationManager`): per-bot filter in `isEdgeUsable(graph,map,bot,skillsEnabled,edge)` (skill edges need skillsEnabled && has-that-skill), threaded through `runSearch` (10-arg walk-only overload kept for tests/probes). Skill bots BYPASS the shared route cache and plan via `findNextEdgeWithSkills` = **TWO-PASS** (walk-only baseline vs skill-enabled), take the skill path only if `walkCost − skillCost ≥ skillSavingsThreshold(walkCost)` [60% saving at `SKILL_CLOSE_GATE_MS=1200` easing to 5% at `SKILL_FAR_GATE_MS=6000` — distance-scaled, "far → use even to straighten a walk"]. NOT a per-edge penalty (a flat penalty can't separate close/far — it discourages long teleport chains). Execution: `tryExecuteTeleport` (teleportTo + deduct MP), `tryExecuteFlashJump` (pendingFlashJump + initiateJump). `reuseCommittedEdge` retires a committed skill edge if MP/meso later drops (skill-edge check short-circuited to skip cost for non-skill edges every tick).
- INTRA-region runtime express (same-platform straight-line speedup the region A* can't hold as an edge): `tryIntraRegionSkillHop` in `resolveTarget`, same-region far target → blink (teleport) or dash (flash jump) toward the target. Safeguards: lands in the SAME region only (no fall-off into a gap), MP-affordable, `INTRA_EXPRESS_MIN_PX=300` (closer = walk), `INTRA_EXPRESS_COOLDOWN_MS=250` cadence. Both skills (user chose both).
- GATE beyond skill+threshold: `botCanUseMovementSkill` = has skill && **>40% MP** && **>500k meso** (MP preserves combat/heal reserves; meso is a humanlike well-off-bot tell — poor bots conserve and walk). Dynamic → checked at plan time; MP deducted per cast (`mpCon` from `skill.getEffect(lvl).getMpCon()`).

**UPDATE GRAPH_VERSION 64 — flash-jump edges now carry an X launch window** (same `expand*LaunchWindow`/`find*Boundary` treatment as ground JUMP, in `BotNavigationGraphProvider`). FJ used to emit ONE POINT-EDGE PER ANCHOR (launchMinX==launchMaxX==anchor.x) — a wide region's interior densification produced dozens of near-identical FJ edges to the same target (the "31 parallel launch-x edges", 293 FJ edges total on Deep Forest 105030000). Now `addFlashJumpEdges` walks `findFlashJumpBoundary` to expand the contiguous launch-X span where FJ lands in the target region AND a plain jump from the same X does NOT (position-aware "FJ only adds reach" guard; JUMP+FJ windows union covers all reachable X with no gap), emitting ONE windowed edge (adjacent anchors dedup via edgeKeys). New `FlashJumpLandingCache` (mirrors `JumpLandingCache`) keeps the boundary walks cheap. Execution-side consistency (`BotNavigationManager`): `selectedJumpLaunchX` now includes FLASH_JUMP (steers to a random in-window launch X + `deepenJumpLaunchOneStep`, exactly like JUMP), and the `FLASH_JUMP_LAUNCH_TOL=12` bandaid in `isWithinJumpLaunchWindow` is GONE — a real window makes FJ gate identically to JUMP (tolerance 0). This is the root-cause fix for the old "Hermit stuck on `fj-pos`" bug (a 1px window was practically unreachable). Generation symmetry now: JUMP/DROP/rope-grab/rope-exit/FLASH_JUMP all windowed; TELEPORT too (below).

**UPDATE GRAPH_VERSION 65 — teleport edges carry an X launch window too.** `addTeleportEdges` got the same treatment (`expandTeleportLaunchWindow`/`findTeleportBoundary`/`isValidTeleportLaunchX`, predicate = teleport from X lands in target region): one windowed edge per (anchor,intent) instead of a point-edge per anchor. KEY DIFFERENCE from JUMP/FJ: teleport dest depends on launch X (blink = ±range from current pos), so a fixed `edge.endPoint` is only the REPRESENTATIVE landing — execution (`tryExecuteTeleport`) now computes the dest LIVE from the bot's actual position via the physics SSOT `BotPhysicsEngine.teleportLanding(map, botPos, dirX, dirY, RANGE, SNAP)`, recovering intent direction from sign(endPoint−startPoint) (horizontal = ±range in x → dirX; vertical = same x → dirY). Blinking to a fixed endpoint from a non-representative X would be an illegal off-range hop — the live recompute keeps every in-window launch legal. Execution-side consistency: new `isWithinTeleportLaunchWindow` (twin of `isWithinJumpLaunchWindow`) replaces the old anchored `isReadyForEdge` gate in both `tryExecuteTeleport` and `shouldUsePreciseTarget`; `selectTeleportWaypoint` steers to the nearest in-window x (was: walk to the single startPoint). **FLASH-JUMP BROADCAST PACKET (client-verified, fixes "bot jerks off-screen on the activation frame then snaps back").** `BotMovementManager.broadcastFlashJump` used to emit a LONE type-6 ("fj") fragment. Per the v83 client `CMovePath::Decode @ 0x0068a33c`: a type-6 fragment does NOT read x/y from the packet — it sets the element's position to the PREVIOUS fragment's position and stores the two packet shorts into the velocity slots (`[esi+6]/[esi+8]`). The decoder's "previous position" register is seeded with packet-header garbage, so a lone fj fragment renders the bot at a garbage off-screen position for one frame until the next per-tick absolute (cmd-0) snaps it back. Every real flash-jump capture (`logs/monitored-packets-flashjump*`) leads with an absolute cmd-0 and sandwiches the fj between absolutes — never lone. FIX: broadcast a 2-fragment path `[cmd0 absolute @ current pos] + [cmd6 fj]`, fj duration 0 (matches captures). Note the fj two shorts are velocity slots, not a position delta; the dash ANIM is triggered by the fragment TYPE, so the exact magnitude is cosmetic (current per-tick delta ~±27 vs real ~±125/±172 — left as-is since behavior/position is already correct via the cmd-0 ticks).

**TELEPORT BROADCAST / COOLDOWN WALK (packet capture `monitored-packets-teleportspd109jump105.log`).** Real Teleport movement packets use normal walking fragments around the blink: cmd4 at the launch point, cmd3 at the landing point, then an immediate cmd0 landing/settle fragment; casts are ~580-620ms apart at chain speed, but the cooldown only gates the next cast, not walking/jumping. Bot fix: `broadcastTeleport` now emits `[cmd4 origin] + [cmd3 dest] + [cmd0 absolute dest]` so observers settle at arrival without waiting for the next movement packet, and `selectTeleportCooldownWaypoint` walks horizontally inside the current teleport launch window while `tele-cd` is active. `teleportTo` still clears velocity/intent, preserving the real slippery-map momentum reset after the blink.

**TELEPORT FRAGMENT BYTE LAYOUT (client-verified, fixes "teleport animation lingers ~1s / stutters").** The server (`AbstractMovementPacketHandler`) parses cmd 3/4 as `x, y, xwobble(2), ywobble(2), stance(1)` — but the v83 CLIENT (`CMovePath::Decode @ 0x0068a33c`, jump-table branch `0x68a463` for cases 3/4/7/8/9) decodes the SAME 9 payload bytes as **`x(2), y(2), fh(2), stance(1), elapse(2)`** (fh also stored to the path's last-fh slot; velocity slots zeroed). `broadcastTeleport` used to build frags in the server-parse layout with stance as the LAST byte, so observer clients read `elapse = stance<<8` ms (stance 4 → 1024ms, prone 0x0A → 2560ms) — the teleport frame lingered for that long instead of blinking. Every real capture (`logs/monitored-packets-teleport*`) carries `[fh][stance][elapse=0]`: cmd4@origin has the ORIGIN foothold id, cmd3@dest always fh=0 (arrival treated as airborne until the settle cmd0 carries the real fh). Fixed in `BotMovementManager.putTeleportFrag` (+ origin-fh resolve in `broadcastTeleport`); regression asserts in `BotMovementManagerTest.shouldBuildTeleportPacketWithImmediateLandingFragment`. General lesson: **server parse layout ≠ client decode layout for the same movement command — always author broadcast frags against `CMovePath::Decode`, not `parseMovement`** (same trap class as the lone-fj-fragment bug above).
