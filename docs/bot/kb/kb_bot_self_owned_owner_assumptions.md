Bots were first designed assuming `entry.owner` is a distinct, online, real human. Self-owned bots (`@botme`/`@botparty` takeover + server-generated managed population bots) have `owner == entry.bot` and `owner.getClient()` is a `BotClient`. This breaks owner-assumption code; many such bugs found.

**Two traps:**
1. An early `owner == bot` bail/guard that fires BEFORE resolving the real intent (leader, crew). Archetype fixed in `BotManager.resolveFollowAnchor` (commit 8fcccd719): moved explicit `followTargetId` party/sibling resolution ahead of the self-owned null guard so self-owned transit-followers get an anchor and catch up across maps via `syncFollowMap` (legal portal route ≤ MAX_FOLLOW_TRAVEL_HOPS=4, else warp).
2. `getBotEntries(owner.getId())` to find "my group" — for a self-owned bot `owner.getId()==bot.getId()`, so it returns a group of ONE (its crewmates are keyed under their own ids). SSOT fix: `BotManager.shareCandidateEntries(ownerId, needyEntry)` = owner stable PLUS, for a crew bot (`crewGroupId != null`), same-map `crewMatesOnMap`. Used by potion/ammo/rock share donor picks.

**Offline-owner identity:** `BotEntry.owner` is only the live character reference and becomes null when a
human owner logs out. It must not be used to infer that the bot was created ownerless. `BotEntry` records
both the stable `ownerCharId` (used by ticks/retasking and the owner-away town cluster) and the creation-time
`selfDrivingOwnership` classification. `BotManager.isSelfDrivingBot` uses that classification plus the
dynamic `ownerIsBot` takeover case. Otherwise a logged-out player's companions are misclassified as
managed bots, inert-autopilot self-heal restarts their grind, and the normal owner-away town-idle flow is
bypassed.

**Gate idiom for self-owned supply share** (potion/ammo/rock): bail on `owner == null || (owner == bot && entry.crewGroupId == null)` — solo self-owned skips, crew self-owned shares like an owned party. Owner perks stay gated, not removed.

**Fixed:** resolveFollowAnchor (8fcccd719); BotRockManager rock-share (ff7e531ac, matches BotPotionManager:537 / BotAmmoManager:74); grind region-occupancy now party-weighted (0538b83a2 — every live char in region: same-game-Party weight 1, outsiders weight 2 for kill-steal avoidance; crews/owner/dynamic all share a real Party so getPartyId() covers all sources); handleWhisperToBot (0538b83a2 — resolves entry under active owner so gm6 admin can whisper-command a foreign/self-owned bot, binds admin as debug commander so reply whispers back to the command giver not owner==bot).
**Fixed:** crewmate-to-crewmate trade timeout (9939a7e9a). `BotInventoryManager.tickManualTrade` gated the recipient's auto-join (`isPeerBotTrade`) on the donor being `isAuthorizedOwner(donorId, entry.owner.getId())` — fails for crew bots (self-owned, owner==self), so the recipient never `Trade.visitTrade`d and the donor hit "trade request timed out" despite the recipient accepting the offer in chat. Fix = extracted `isPeerTradePartner(entry, partnerBot)` = same human owner OR same `crewGroupId`. (commanderOrOwner returns the bot itself for self-owned, so the line-307 `commander==null` guard already passes — the join gate was the only blocker.)

**RESOLVED (2026-06-23) — managed crew/party SCATTER was NOT an owner bug (red herring; don't re-chase it).** This is the rare case where owner-assumption code was INNOCENT: population bots are self-owned (`owner == bot`, `BotManager.registerSpawnedBot(botChar.getId(), botChar, botChar)` at :572/696/968), so the `owner==null` guards in `tickPartyCohesion` (~:1327) and `resolveFollowAnchor` (BotManager:2132) never fired. Real root cause (pinned via `/api/botdebug`: all 44 online bots `apParty=false`, transit/following=0, despite all being in real parties): the crew's shared party directive `BotAutopilotManager.startParty` is issued ONCE at crew bring-up (`BotScheduler.formCrewParty`, `runStartParty=true`) and NEVER retried — the steady sweep passes `runStartParty=false`. If that one call no-ops (bots' `getMap()` null mid-login, or `decideParty` returns null under cold load — caught→null at BotAutopilotManager:1476), `autopilotParty` is never set, the cohesion gate (`BotAutopilotManager:581 if(entry.autopilotParty...)`) never runs, and every member falls to solo autopilot → scatter. **Fix (commit 16d8270bf):** `formCrewParty` also (re)issues `startParty` when an online crew is partied but `live.stream().noneMatch(e -> e.autopilotParty)` — self-healing, self-limiting (stops once set). Needs server restart to activate; verify by re-querying `/api/botdebug` for `apParty=true`. **Straggler false-wait — FIXED (commit 7d4d052ab):** embark cohort gate. New `BotEntry.autopilotCohortMember`, set in `applyPartyPlan` = `member.bot.getMapId() == leaderMapId` (leader = members.get(0)). Off-cohort members travel INDEPENDENTLY to the shared dest: gated in `tickPartyCohesion` (off-cohort follower → exitTransitFollow + return null → normal travel) and `waitingForStragglers` (skip off-cohort, leader never waits on them); reset in `clear()`. Re-snapshotted each new party destination, so off-cohort members reconverge at dest then join the cohort on the next embark. Rule (user): "only bot in same map on journey embark forms cohort; the rest go independently." Both this and the self-heal need a server RESTART to activate; verify via `/api/botdebug` (apParty=true, crews converging). Edits to BotEntry/BotAutopilotManager were verified working-tree-clean (only my hunks) before commit despite concurrent-session ownership.

**Fixed:** PQ/event death (55bf77af6). Old respawnBot warped the corpse to owner/anchor — never a legal player move + no-op for self-owned. Verified real-player flow: on death the corpse lies at the tomb (no warp/auto-kick); pressing OK -> ChangeMapHandler -> eim.revivePlayer (script playerRevive: unregisterPlayer + end(eim) if leader leaves or team drops <= minPlayers via isEventTeamLackingNow) -> chr.respawn(getReturnMapId()). No in-instance revive in stock scripts (only Wheel of Fortune cash item). Bot now mirrors it: handleDeadTick keeps the bot dead (re-check every DEAD_EVENT_WAIT_MS=2s) while hasLiveEventMateInMap (a non-self EIM member alive in bot's map); once none remain, respawnBot runs botEim.revivePlayer(bot) + bot.respawn(getReturnMapId()). Standard EIM only; CPQ (no tomb, Character.playerDead returns early) + owner-event/PqHook-non-member cases keep legacy respawnAtOwner. Consequence (by design = real player): a bot reviving as party leader / at min-team ends the PQ for everyone.
