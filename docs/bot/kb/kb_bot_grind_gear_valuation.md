How the bot values gear (farm-worth, keep/sell, quest rewards, scrolling) and where the SSOTs live:

- **Valuation metrics** (9c6a5e6a5): `equipValue = offenseValue + survivalValue` (BotScrollManager) is the SSOT for "how good is this piece" in keep/sell/drop-vs-worn/reward decisions. `survivalValue` covers WDEF/MDEF/HP/MP/avoid/move at small weights; ACC is deliberately excluded (owned by the aspirational-accuracy effective-DPS model — valuing it per-item would double-count). `offenseValue` stays the pure-DPS sub-metric for scroll EV (`bestScrollEvPerSlot`) and is deliberately speed-blind and II-free — it's called from unit-test contexts where ItemInformationProvider can't load; never add II lookups inside it. `potentialValue` bases on `equipValue`; the grind Monte Carlo roll score and worn-baseline normalizer (`totalWornValue`, package-visible) use `equipValue` too, keeping marginal E[max(0,roll−worn)] in one unit.
- **Wearability/farm/scroll gate** = `BotScrollManager.levelsUntilWearable` (job/level/stat via `ii.meetsEquipRequirements`; shield slot -10 returns -1 when the worn weapon is 2H — a bowman's weapons are all 2H so shields are never farmable/scrollable for it). For weapons (slot -11) it must use **`BotEquipManager.isPreferredWeapon`** (the job's actual attack-skill weapon + mage-MATK exception). Since the fallback-weapons change (1071d5d98) there are TWO weapon predicates — do not confuse them: `isWeaponCompatible` = merely "can physically equip" (any non-`NOT_A_WEAPON`); it feeds the autoEquip/optimizer DP pool so a fallback weapon can be worn in a pinch (the `weaponRank` tiebreak in `scoreNode`/`compareScores` ensures a preferred weapon wins when owned), and using it in the farm/scroll gate once let a Gunslinger treat a Surfboard as farmable/scrollable. The offer path (`BotOfferManager.isWeaponOfferCompatible`) deliberately stays on the wide predicate (it only pre-filters candidates for the DP + reserve guard, which self-correct). Reserve (`selectOwnedItemsForSelfReserve`) gates on `isPreferredWeapon` but only skips a fallback weapon when `ownsPreferredWeapon` (owned-set includes EQUIPPED) — keeps the bot's sole fallback when it has no real weapon. The autoEquip optimizer does NOT use this gate; it builds pools via `canWearEquipment` and enforces exclusivity inside the DP (`slot == -10 && is2H` skip, `isOverall` blocks pants -6).
- **Cross-slot bars**: `equipGain` calls `gearBar(...)` → `crossSlotBar(combinedBest, pieceBest, partnerBest, candidateIsCombined)` = `max(combined, piece+partner) - keptPartner`. Families: overall(-5, `ItemConstants.isOverall` = id/10000==105) vs top(-5)+pants(-6); 2H vs 1H(-11)+shield(-10). Ensemble pieces cached in `wornScoreBySlot` under synthetic positive keys (105 top, 106 overall, 111 1H, 112 2H; real slots are negative).
- **Weapon speed**: `weaponSpeedFactor(itemId)` = 720ms / `BotEquipManager.weaponCycleMs(itemId)` (WZ attack animation × speed tier — the same number `scoreNode` uses for the optimizer's true DPS benchmark; returns 0 → factor 1.0 when WZ unavailable). Applied to BOTH `sampleRollScores` and `bestOwnedScore` for slot -11 so a slow high-watk spear must out-roll a fast one by the cycle ratio.
- **Quest gear rewards** (f23ac9b18) ride the SAME SSOT as grind/maker/gacha: `BotQuestManager.computeRewardGain` (the `rewardGain` seam, returning `RewardGain(dpsGainFraction, consumableMeso)`) values a reward equip via `BotGrindAdvisor.expectedAcquireGain(bot, ii, itemId, cleanSampler, 1, barCache)` (cleanSampler = `sampleEquipScores(...,(base)->base)`), scrolls via `BotGrindAdvisor.scrollGains.gain`, divided by `BotGrindAdvisor.totalWornValue` → a %DPS fraction exactly like GearProspect.dpsGainFraction. `scoreQuest` converts: `uniqueBonus = dpsGainFraction * baseline * GEAR_PAYBACK_HORIZON_MINUTES(240=4h) + consumableMeso*REWARD_EXP_PER_MESO`. baseline CANCELS in value/cost → gear-quest worth is grind-rate-invariant (only the exp reward scales by the quest/mob expRateRatio). There is no flat per-offense constant and no separate scroll-reward EV path. See [[kb_bot_fetch_quests]].
- **Scroll planner value lenses** (a38171b6f): an item's OWN reproduction-meso curve (`BotScrollValuer`) tracks base rarity/cost, not combat usefulness — a score-0 pricey-base cape once out-valued a worn score-10 cheap-base cape and was proposed "as an upgrade" (scroll-debug-Preston.txt). `BotScrollPlanner.EquipCandidate` therefore carries TWO lenses. `value` = own repro curve, used by the profit/scroll-to-sell pass (still `SCROLL_FOR_PROFIT_ENABLED=false`). `combatValue` = the **slot-substitution curve** (`BotScrollManager.buildSlotCurves`: pointwise MIN over the distinct owned same-slot bases' repro curves, each valid only up to its reachable ceiling, clamped flat past all ceilings) with the worn rival **baked in**: a bag spare's terminal value is `slotCurve(max(v, wornScore))` (the bot wears the better of the two) and its boom branch pays `destroyedValue = slotCurve(wornScore)` (booming a spare keeps the worn piece; a worn piece's boom is 0, still guarded by `hasFallbackForSlot`). "Must beat the worn item" is priced by the value function itself — there is NO domination gate or worn-value floor (two earlier gate attempts, a slot-count proxy and an all-success ceiling, each bred its own bug, and any hard ceiling kills the legitimate endgame play: cheap low-odds parlays whose convex upside beats the ticket price). Hopeless catch-ups price out naturally (every sub-worn state is worth exactly the worn state, so attempts are pure cost); an endgame lottery on a fresh base stays viable. Regression tests: `improbableCatchUpOnAWorseBaseIsRefusedNaturally`, `endgameLotteryOnAFreshBaseStaysViable`, `boomedSpareKeepsTheWornValueInTheDestroyBranch`, `prefersScrollingTheWornCopyOverItsTrailingSpares` (BotScrollPlannerTest).
